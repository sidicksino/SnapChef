# Task Tracking: Phase 3 (Mobile App Frontend)

- `[x]` **Initialize App:** Create Expo project named `frontend`.
- `[x]` **On-device model, then replaced:** Trained/exported a YOLOv8 `.tflite` model (see `ml/train_colab.ipynb`) and wired it up end-to-end with `react-native-fast-tflite`, including recovering lost class labels and fixing a TFLite-engine-version incompatibility along the way. Retired after real-device testing (nano then yolov8s, several confidence-aggregation strategies) consistently showed it only ever confidently found one dominant item per busy photo — a training-data ceiling (the dataset is mostly single-item crops, not cluttered fridge scenes), not something app-side tuning could fix. Replaced by Gemini vision-based detection (see Integrate API below); `react-native-fast-tflite`, the model file, and the on-device detection code have been removed.
- `[x]` **Setup NativeWind:** Install and configure Tailwind CSS for React Native.
- `[x]` **Setup Vision Camera:** Install `react-native-vision-camera` (for real camera capture — ingredient detection itself now runs server-side via Gemini, not on-device).
- `[x]` **UI: Splash & Onboarding:** Build the blue-blur premium splash and onboarding screens.
- `[x]` **UI: Auth:** Login and Sign Up screens, now wired to the real backend (see Integrate API below).
- `[x]` **UI: Home & Scan:** Magazine feed home screen (real recipe data) and a real camera capture flow are built, plus a photo-library picker (`expo-image-picker`, for the Simulator's lack of camera hardware and as real feature parity) and a manual ingredient-entry flow. "Use Photo" uploads the captured/picked image to `POST /api/recipes/detect-ingredients` (Gemini vision, see Integrate API) and hands the results to the manual-entry screen, pre-filled and still editable, instead of auto-submitting unverified detections. A Skia-drawn progress ring (`components/detecting-ingredients.tsx`) covers the wait. Verified end-to-end on a real iPhone (not just the Simulator).
- `[x]` **UI: History & Profile:** Real 5-tab bottom nav (Home/Search/Scan/Saved/Profile), the Saved masonry gallery (real recipe data), and the Spotify-style Profile screen (real account data, stats, dietary preferences) are all built.
- `[x]` **Integrate API:** Axios client (`src/lib/api-client.ts`) with JWT auth (stored via `expo-secure-store` on native, `localStorage` on web — SecureStore's web build is a no-op stub) wired end to end: register/login/logout with real error messages, GET/PUT `/api/users/me` (profile + dietary preferences), GET `/api/recipes` + `GET /api/recipes/{id}` (Home + Saved + a per-recipe detail screen at `recipe/[id].tsx`), and a manual-entry screen (`generate-manual.tsx`) hitting the real `POST /api/recipes/generate` + `POST /api/recipes` so the whole loop works without waiting on camera detection. Verified end-to-end against the real local backend (not mocked) via Playwright on web; native verified interactively on a real iPhone. Recipe generation runs on Gemini (not OpenAI) — `backend/routers/recipes.py` points the `openai` SDK client at Google's OpenAI-compatibility endpoint with the user's own key in `backend/.env`. Generation also produces a real Gemini-generated photo per recipe (`generate_recipe_image`, served from `/static/recipe_images/`) shown on the result screen, recipe cards, and the detail screen. `POST /api/recipes/detect-ingredients` sends an uploaded photo to Gemini's vision input to identify ingredients, replacing the earlier on-device model (see above) — real, verified results, not a mock, on both native and web (this one has no native-only dependency, so web finally gets real detection too, not a placeholder).
